<research_findings>
Measured against the running dev Jellyfin (`docker exec emby-auth-dev-jellyfin-1`), so the styling decision is not a guess:

- `/jellyfin/jellyfin-web/themes/dark/theme.css` defines `.button-submit{background:var(--jf-palette-primary-main,#00a4dc);...}` and a `:hover` and `:focus` variant. It defines **no** disabled variant.
- The bundled `emby-button` CSS defines `.emby-button`, `.emby-button.block`, `.emby-button.show-focus:focus`. It defines **no** `[disabled]` or `:disabled` rule.
- The only disabled-control convention the dashboard ships is `.emby-select[disabled]{appearance:none;background:none!important;border-color:transparent!important;color:inherit!important}` — it flattens the control so it stops reading as interactive.
- The themes emit `--jf-palette-action-focus`, `--jf-palette-action-hover`, `--jf-palette-action-selectedOpacity`. They emit **no** disabled token, so there is no dashboard variable to key off.

Conclusion: Jellyfin 12.1 has no reusable convention for a disabled `emby-button`. The existing markup is not missing a class. One small scoped rule is required. Use `opacity` rather than a color, because opacity dims whatever the active theme paints and stays correct across all five shipped themes; a hardcoded color would break on the light theme. `0.38` is Material's `action.disabledOpacity`, and the Jellyfin palette variables are Material palette names, so the value follows the same system the dashboard is built on.

`.emby-button` sets `cursor:pointer`, which is the second signal that reads as live, so the rule also sets `cursor:default`.

The page's inline `<script>` already lives inside `#EmbyAuthConfigPage`, which proves Jellyfin injects that element's subtree. The `<style>` element goes inside the same element for the same reason.
</research_findings>

<scope_boundaries>
IN scope:
- A second status element for settings-level load and save failures, under Save.
- A shipped style rule that dims a disabled Save.
- Disabling Save when a save is attempted (locked decision), and leaving it disabled after a failure.
- Clearing a stale settings-failure message on a successful load.
- **WR-04, now required rather than optional.** Splitting the two status elements means the load-failure path no longer overwrites `#EmbyAuthMigrationSummary`. Without clearing, a successful load followed by a failed one would leave BOTH a stale summary line ("Users on the Emby login method: 3.") and a stale user list on screen, under a message saying the settings cannot load. The split turns WR-04 from a cosmetic follow-up into a regression this change would otherwise introduce, so the fix ships here.
- One sentence in `docs/settings.md` for the new save-path behavior, per the repo rule that docs stay accurate when behavior changes.

DECIDED, not deferred — the successful-save path. The locked decision covers "disables on attempt" and "stays disabled after a failure" but is silent on success. Save re-enables on a successful save. Rationale: the stale-state risk the locked decision guards against does not exist after a success (the page state and the saved state agree), and every other Jellyfin dashboard page leaves Save live after a save. Leaving it disabled would force a reload between two ordinary edits. If the user disagrees, the change is one line in the success handler.

OUT of scope, stated rather than silently dropped:
- No color change to the failure message. The themes offer `--jf-palette-error-main` (#c62828) and `--jf-palette-error-light` (#d15353); neither holds contrast across both the dark and the light theme, and the gap asks for placement plus a visibly disabled Save, not a red message. The new element uses the same plain `<p>` shape as the existing summary.
- No rewording. Both message strings stay byte-identical.
- No change to `02-UAT.md` or `ROADMAP.md`.
</scope_boundaries>
