<objective>
Turn the proven merge into a published catalog: enumerate every release from the GitHub Releases API, rebuild the manifest from what the releases actually contain, publish it to GitHub Pages from a separate workflow, and have that workflow verify its own published output.

Purpose: plan 06-01 proved the document Jellyfin needs can be built and installed from. This plan is what puts that document at a stable URL and keeps it correct on every release without any workflow gaining permission to write to the repository. The rebuild is stateless, so a failed Pages deploy is re-runnable and the manifest can never claim a version whose release does not exist.

Output: the `rebuild` and `verify` actions in `scripts/manifest.sh` with their bats coverage, a `manifest` mise task, `.github/workflows/pages.yml`, and the matching rows and steps in `docs/development.md`.
</objective>

    - Prints the path it wrote, the way `scripts/package.sh build` prints the path of its zip.

    The `verify` worker takes a URL:

    - Fetches it with `curl -fsSL` into a file under the scratch root, capturing the call so a non-2xx response or a connection failure produces its own message naming the URL.
    - Refuses with a distinct message when the body does not parse as JSON, and again when it parses but holds zero version entries across all packages. An empty document is the shape a half-finished deploy would leave, and it is indistinguishable from a working catalog to anyone who does not count.

On a mismatch it refuses, naming the version, the recomputed value and the recorded value.
    - On success prints one line saying how many version entries it checked and against which URL.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Releases API → the published manifest | Data fetched with the workflow token becomes a document served to unauthenticated Jellyfin servers. |
| the workflow's `GITHUB_TOKEN` → the repository | A workflow definition is code a pull request can propose; whatever the token can do, a compromised definition can do. |
| GitHub Pages → an administrator's Jellyfin server | An unauthenticated fetch over HTTPS. Nothing downstream re-checks the manifest's provenance. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-01 | Tampering | the `jq` calls in `scripts/manifest.sh` | high | mitigate | Every value written into the manifest goes through a `jq` argument, never interpolation; the merge path plan 06-01 proved is the only writer, and `rebuild` calls it rather than carrying a second one. |
| T-06-02 | Tampering | a corrupted or tampered release asset reaching the manifest | high | mitigate | `rebuild` routes through `merge`, which recomputes every zip's MD5 before the entry is written, and `verify` recomputes them again against the published document after deploy (D-02, D-05). Tests W, Y and Z prove each refusal. |
| T-06-03 | Elevation of Privilege | `.github/workflows/pages.yml`'s job tokens | high | mitigate | Job-level `permissions` grant a read scope on contents plus `pages: write` and `id-token: write` only, each with an inline comment naming its consumer; no write scope on repository contents anywhere, asserted by a comment-stripped negative check; `persist-credentials: false` on every checkout; the pedantic zizmor persona runs over the file in `mise run lint`. |
| T-06-05 | Information Disclosure | workflow logs | medium | mitigate | The only credential is the workflow's own token, supplied through an `env:` block and never echoed. No workflow expression is expanded into a `run:` command string, which is both the template-injection mitigation and the reason a value cannot reach the log through the command line. |
| T-06-06 | Tampering | the manifest published while a release does not exist | medium | mitigate | The rebuild is stateless and enumerates the live releases, so the published document cannot name a version with no release behind it; the entry-count invariant refuses the opposite case, where a release exists and its entry did not make it in. |
| T-06-10 | Spoofing | the Pages build-type setting | low | accept | Setting the Pages build type requires the Administration permission, which a workflow token cannot be granted, so this workflow cannot perform it and does not try. | T-06-SC | Tampering | npm/pip/cargo installs | high | mitigate | This plan runs no package-manager install.
