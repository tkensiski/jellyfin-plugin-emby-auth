  <instructions>
    Everything automatable is done. `.github/workflows/pages.yml` is written, pinned, pedantic-zizmor-clean and merged; `mise run manifest` rebuilds the manifest locally; the version and the dated changelog are committed.

    This one step is not automatable, and the reason is specific rather than a preference. The REST endpoint that creates a Pages site and sets `build_type` sits under GitHub's **Administration** repository permission. That permission is not in the set a workflow's `GITHUB_TOKEN` can be granted at all — `pages: write` covers deployments, not the site's build-type setting. A step in `pages.yml` that tried it with the workflow token would fail with a permission error on every run. So it is the repository settings page, or a `gh api` call you run yourself with your own authentication.

    Through the settings page: open the repository's Settings, then Pages, and under **Build and deployment** set **Source** to **GitHub Actions**.

    Or, with your own authenticated `gh`, the equivalent call is a POST to `repos/{owner}/{repo}/pages` with `build_type` set to `workflow`; if the site already exists, the same shape as a PUT updates it.

    Either way it is done once and never again. A repository with no Pages site of build type `workflow` makes the deploy step fail outright — not with a checksum or content mismatch, but with a deployment-target error — which is the signal to come back to this step.
  </instructions>
