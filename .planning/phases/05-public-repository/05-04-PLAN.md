    The section states these facts and nothing beyond them.

    What was tested: Jellyfin 12.1.0 and Emby 4.10.0.40, in local containers. Say that explicitly — no production server has run this plugin.

    What `targetAbi` is: define the term in plain words before using it. The release zip's `meta.json` and the plugin repository `manifest.json` both carry a `targetAbi` value, and for this build it is `12.1.0.0`. It declares the **minimum** Jellyfin version the plugin asks for. Jellyfin decides which catalog entries to offer by comparing the version it parses from `targetAbi` against the server's own version and keeping the entries whose `targetAbi` is less than or equal to it. So a server older than `12.1.0.0` is never offered the plugin, and a server newer than it is offered the plugin and will install it.

    What that means for an administrator: there is no upper bound in the value, so a Jellyfin release newer than 12.1 will install this plugin even though nobody has tested it there. Write that as the consequence it is. Do not write a sentence that says, suggests, or can be read as saying that a newer Jellyfin is supported, works, or is expected to work. A maintainer asked what `targetAbi` was during the phase discussion and the answer shaped this whole section — write it for a reader who has never heard the term.

    Keep the two version strings distinct. `12.1.0` is the tested Jellyfin version and `12.1.0.0` is the `targetAbi` value, which is the same number with a fourth part appended by `target_abi()`. Write each in its own form where it belongs and do not present them as the same string — a reader comparing them against their server's version needs to know which one Jellyfin parses.

    Change nothing else in this task. In particular, leave the Status line alone: its claim that the plugin is not published to a plugin repository stays true until Phase 6 publishes the manifest.
