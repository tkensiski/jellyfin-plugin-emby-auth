Two of the fixes are substantive rather than cosmetic: `release.yml` gains the concurrency block that stops a release being killed mid-upload, and the `ci-success` job gains a name chosen so the release gate keeps working.
Output: `name:` on all five jobs, a `concurrency:` block in `release.yml`, and `--persona=pedantic` on the existing zizmor line in `[tasks.lint]`.
</objective>

  <action>
    Three edits, all inside the two workflow files. Batch them so each file is written once.

    `.github/workflows/ci.yml` — add a `name:` field directly under each of the four job keys. Give `lint`, `test`, and `e2e` descriptive names: `Lint`, `Build and test`, and `End-to-end tests`. Give `ci-success` the name `ci-success`, byte-identical to its job id. That last one carries no new information and that is the accepted trade (D-09): a job's `name:` becomes its check-run name, and the commits API for this repository returns exactly the four check runs `ci-success`, `e2e`, `test`, `lint` today. Renaming the aggregate would rename the check run `scripts/release-gate.sh` queries by `check_name`, and would break any branch-protection rule requiring `ci-success` once that becomes available. Add a short comment above the `ci-success` name field recording why it repeats the job id, so a later contributor does not "improve" it.

    `.github/workflows/release.yml` — add a `name:` to the `release` job: `Build and publish the release`. Then add a workflow-level `concurrency:` block, placed after the top-level `permissions:` block and before `jobs:`, matching `ci.yml`'s shape: `group: ${{ github.workflow }}-${{ github.ref }}` with `cancel-in-progress: false`. Add a comment above it stating why the value differs from `ci.yml`'s `true`: a release run can be interrupted after `gh release create` has made the release but before every asset is uploaded, so releases queue and are never killed. Note that zizmor's `concurrency-limits` audit only requires that a `concurrency:` block exists — its generic remediation text suggests `true`, and following that text here would be wrong.

    Confirm the two `permissions:` grants in `release.yml` still carry the inline comments plan 05-01 added; the `undocumented-permissions` audit needs a comment on each explicit grant. Leave the workflow-level `contents: read` in both files unchanged — it was not in the measured finding set.

    Change nothing else in either file. No new `uses:` step is added by this plan, so no new SHA pin is needed.
  </action>
