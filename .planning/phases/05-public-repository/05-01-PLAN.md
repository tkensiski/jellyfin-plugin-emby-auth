RESEARCH.md's Pattern 1 shows the `--jq` form; this is the same query with the filter moved one process to the right, for fake fidelity. The `check_name` filter stays server-side, and the endpoint's `filter` parameter defaults to `latest`, so a re-run of `ci-success` on the same SHA does not produce a second array element.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| pushed git tag → `release.yml` | A `v*` tag is the only trigger for a release. Anything the tag points at reaches the publish path. |
| `release.yml` job → GitHub REST API | The job's `GITHUB_TOKEN` crosses into the API with whatever scopes the `permissions:` block grants. |
| GitHub check-runs response → `scripts/release-gate.sh` | Untrusted-shaped JSON (empty array, null conclusion, error body) decides whether a release is published. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-01 | Tampering | `.github/workflows/release.yml` `release` job | high | mitigate | `scripts/release-gate.sh check` runs before `mise run test` and `mise run package`; it exits 0 only for exactly one `ci-success` check run at `completed`/`success`, so a release cannot be built from a commit whose suite never passed |
| T-05-02 | Spoofing | `scripts/release-gate.sh`, the `gh api` call | high | mitigate | An API call that fails produces its own refusal message and exit 1, tested explicitly (Task 2 Test 11); a 403 caused by a missing `checks: read` grant can never be read as "no `ci-success` run yet" and silently become a pass |
| T-05-03 | Elevation of Privilege | `release` job `permissions:` block | medium | mitigate | Exactly `checks: read` is added to the existing `contents: write`; no broader scope, and each grant carries an inline comment naming its consuming step |
| T-05-04 | Tampering | the check-runs response shape | medium | mitigate | The script matches `conclusion == "success"` exactly rather than excluding a known-bad list, so an unenumerated conclusion (`neutral`, `action_required`, `stale`) refuses; Task 2 Test 9 proves it |
| T-05-SC | Tampering | npm/pip/cargo installs | low | accept | This plan installs no package-manager dependency. `05-RESEARCH.md`'s Package Legitimacy Audit records gitleaks as the phase's only new tool, resolved through mise's `aqua` backend, and it is introduced in plan 05-03, not here. |
</threat_model>
