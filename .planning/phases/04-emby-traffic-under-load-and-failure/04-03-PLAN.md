<objective>
Collapse a burst of concurrent Emby user list refreshes into a single outgoing request.

Purpose: PERF-01. `EmbyUserDirectory.GetStatusAsync` reads a volatile snapshot at `:58`, finds it expired at `:60`, and every concurrent caller then issues its own `GetUsersAsync`. A measured 50-request cold burst collapses from 50 origin calls to 1 with a single-flight guard, at unchanged wall time — the win is Emby-side request count, which a unit test asserts directly.

D-18 authorizes this guard outright. It reverses D-11, which is withdrawn along with D-10 through D-13: D-11 said each bottleneck got a written pass-or-fail threshold before anything was measured, and that this guard lived or died on its own number. The threshold it wanted would have been a request-count bound, which the unit test in Task 2 asserts exactly and for free, so the rig that would have produced the number is not built. Nothing in this plan measures anything.
Output: A guard around the refresh branch only, a request-counting test that drives real concurrency, and a stub HTTP handler that can be driven concurrently and held open.
</objective>

<planner_notes>
**No in-repo analog exists for the guard.** A repo-wide search found no coordination primitive anywhere in `src/` outside `EmbyVerifiedPasswords`'s synchronous `Lock`, which cannot span an `await`. `04-PATTERNS.md` § No Analog Found says to build it from the external source recorded in `04-CONTEXT.md` § External: a `SemaphoreSlim` with `WaitAsync`, plus an explicit re-read of the snapshot after acquiring. That re-read is the whole correctness argument, and it is the step the two cited stampede write-ups show people leave out.

**The existing stub handler cannot be driven concurrently.** `StubHttpMessageHandler.SendAsync` (`TestDoubles.cs:41-59`) adds to a `List` and dequeues from a `Queue`, neither of which is thread-safe, and it has no way to hold a response open. Task 1 fixes both, because without a held response the concurrency test can pass for the wrong reason: if caller one finishes before caller two starts, caller two sees a fresh snapshot and sends nothing, and the count is 1 with no guard at all.
</planner_notes>

Add a single-flight guard to the refresh branch of `EmbyUserDirectory.GetStatusAsync`, and to that branch only.

Add a `private readonly SemaphoreSlim _refreshGuard = new(1, 1);`. Leave the opening `var snapshot = _snapshot;` read and the staleness test exactly where they are: a caller that finds a fresh snapshot must take nothing and allocate nothing, which is the property `04-PATTERNS.md` § Established Patterns says to preserve.

Inside the branch that today calls `GetUsersAsync`, first `await _refreshGuard.WaitAsync(cancellationToken).ConfigureAwait(false)`. Then re-read `_snapshot` into the local and re-evaluate the same four-part staleness condition against it — the same `now`, the same settings comparison. If the re-read snapshot is fresh, keep it and skip the request entirely. Only when it is still stale do the existing `GetUsersAsync` call, the new `Snapshot` construction, the `_snapshot` assignment, and the `LogUserListUnavailable` call run, unchanged. Release the semaphore in a `finally` so a throwing or cancelled refresh never leaves the guard held.

Use `SemaphoreSlim.WaitAsync`; the C# `lock` statement and the `Lock` type are thread-affine and cannot be held across the `await` on `GetUsersAsync`. Add no caching framework and no package: this is a cache with exactly one key, and `HybridCache` was considered and dropped for that reason.

Update the method's XML doc to say that concurrent callers that find the snapshot stale send one request between them, and that the caller which finds it fresh takes nothing.

Write the four tests in the `<behavior>` block before the guard exists. <threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Jellyfin login path -> Emby user list endpoint | The API key crosses on every refresh; the refresh runs inside Jellyfin's login lock. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-11 | Denial of Service | the guard held while Emby is slow | medium | mitigate | The refresh inside the guard is a single `GetUsersAsync` bounded by the existing 5-second `HttpClient` timeout, so the longest any waiter can be held is that timeout. The semaphore is released in a `finally`, and `ConcurrentReaders_AfterAFailedRefresh_AreNotBlocked` asserts a failing refresh blocks nobody. Without the guard the same burst sends one request per caller to the same slow server, which is worse. |
| T-04-12 | Denial of Service | a cancelled `WaitAsync` leaving the guard held | high | mitigate | `WaitAsync` takes the cancellation token and the release is in a `finally`, so a cancelled or throwing refresh cannot leave the semaphore held. A source assertion requires the `finally`. |
| T-04-13 | Information Disclosure | the API key reaching a log entry through the new path | high | mitigate | The guard adds no log call, and `LogUserListUnavailable` takes only a retry interval. The stub-handler change records requests in tests only and never reaches production code. |
| T-04-14 | Spoofing | a caller reading another caller's snapshot for different settings | high | mitigate | The double-check compares `ServerUrl` and `ApiKey` as well as the expiry, exactly as the first check does, so a caller with different settings never accepts a snapshot built for another. `ConcurrentReaders_WithDifferentSettings_SendTwoRequests` asserts it. |
</threat_model>
