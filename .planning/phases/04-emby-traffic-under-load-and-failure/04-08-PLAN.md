Add exactly two entries to § Limits in `docs/how-it-works.md`, one per cost this version does not remove, each naming the reason it stays.

The first: Jellyfin calls a login method inside a lock, and all logins for names Jellyfin does not know share one lock key, so a burst of first logins runs one at a time. The plugin's Emby calls happen inside that lock, so a slow Emby slows that queue. The reason no fix applies is that the plugin has to ask Emby whether the password is right before it can answer, and the lever that already exists is the 5-second request timeout, which is already described.

The second: Jellyfin saves the account on every accepted login, which is Jellyfin's own account save and not something the plugin performs itself. The reason no fix applies is that the plugin only calls it; what it costs is Jellyfin's to decide.

Write both without a number. Nothing here was measured, and a figure without the machine it was measured on cannot be read. Do not add a separate document for these two entries, do not promise a future fix, and do not describe any other cost as removed: this phase removed the lock a reader waited on, and the duplicate Emby user list request, and those are described where they happen rather than as achievements in this list.

In `CHANGELOG.md`, under the existing Unreleased § Changed heading, add one entry: the record of which password hashes Emby verified moves from a JSON file in the plugin configuration folder to a SQLite database in the plugin's own data folder; the first start after the upgrade imports the old file once and leaves it in place; each record now commits as it is written. Under the existing § Upgrade note heading, add one paragraph: a server that has started this version and then goes back to an earlier one keeps whatever the JSON file held but loses every record written after the upgrade, and each affected user logs in through Emby once more before they can move. Match the voice of the entries already there: plain, factual, no adjective doing persuasive work.
