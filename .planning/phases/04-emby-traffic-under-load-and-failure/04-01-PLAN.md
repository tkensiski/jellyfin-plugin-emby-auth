<objective>
Replace the fingerprint JSON file with a plugin-owned SQLite database, and prove the replacement end to end: one accepted Emby login writes one row through the running plugin inside Jellyfin, and the migration status page reads that row back.

Purpose: FPRT-04. The JSON store makes `Matches` wait on the same `Lock` that `Record` holds across `File.WriteAllText` and `File.Move`, loses a record when the file cannot be read, reports every user as unverified during a read failure, and loses an in-memory record when Jellyfin restarts before the next successful write. A per-row durable commit removes all four (D-14).
Output: A SQLite-backed `EmbyVerifiedPasswords` with the same three public methods, a `Microsoft.Data.Sqlite.Core` 10.0.11 reference that binds to Jellyfin's copy, and a reworked unit suite.
</objective>

<assumption_delta_decision>
**Noun that is now primary:** the fingerprint store.

**Decision: `promote`.** The SQLite database becomes the single store of verified-password fingerprints. The deterministic detector fired on the word "also" in AUTH-05's prose; that is a false positive, because AUTH-05 widens *when* an existing sign-out fires and introduces no second session, token, or identity. The real singular-to-plural transition in this phase is the store: a JSON file and a SQLite database exist on disk at the same moment during the upgrade (plan 04-05).

**Rationale:** the coexistence is one-directional and time-bounded. After plan 04-05 the JSON file is a read-only import source that the plugin reads at most once and never writes, and no code path can write JSON again. Two writable stores would be `add-alongside`; one writer plus a legacy input is `promote`.

**What the JSON file keeps:** it stays on disk after the import, untouched, so a maintainer can still read it and so a crash mid-import loses nothing.

**What would force a different verdict later:** any feature that writes a second on-disk representation — an export, a backup format, or a second plugin instance sharing the records — turns this into `add-alongside` and needs a store abstraction with an explicit primary.
</assumption_delta_decision>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| plugin process -> plugin data folder | The plugin creates and writes a file inside Jellyfin's plugins directory, with Jellyfin's own process identity. |
| Emby-verified hash -> stored fingerprint | A SHA-256 of a password hash crosses into durable storage and must never cross back into a log or an exception. |
| host assembly graph -> plugin assembly graph | The plugin compiles against a NuGet assembly and binds to the host's loaded copy at runtime. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Information Disclosure | `EmbyVerifiedPasswords` log partials | high | mitigate | All three `[LoggerMessage]` partials take the database path and the exception only. `NoLogEntryNamesAHashOrAFingerprint` asserts no entry carries the hash, its lower-cased form, or its fingerprint. A `SqliteException` message can name a table and a column but never a bound parameter value, because every value is parameterized and never concatenated into SQL. |
| T-04-02 | Tampering | SQL built for `Record` and `Matches` | high | mitigate | Both statements bind `$userId` and `$fingerprint` as `SqliteParameter` values. No SQL string in this class is built by concatenation or interpolation. The only literal in any statement is the fixed table and column names. |
| T-04-03 | Information Disclosure | the `.db` file's location and permissions | medium | accept | The file is created under `IApplicationPaths.PluginsPath` with the process umask, the same treatment Jellyfin gives its own database and the same the JSON file had. It holds fingerprints, never hashes or passwords, so its disclosure reveals no credential. Changing file mode is outside ASVS L1 for a single-tenant local server. |
| T-04-04 | Denial of Service | a locked or corrupt database on the login path | medium | mitigate | `Record` catches `SqliteException` and returns, so a store failure never escapes into `Authenticate`, where any non-`AuthenticationException` becomes an HTTP 500. `DefaultTimeout` 5 bounds a busy wait. WAL keeps a reader from blocking on the writer. |
| T-04-05 | Elevation of Privilege | shared cache turned on process-wide | high | mitigate | `Cache` is left at its default and never set to shared, because the setting is process-global and would reach Jellyfin's own connections. A negative source assertion covers it. |
| T-04-06 | Tampering | binding to a mismatched host SQLite assembly | high | mitigate | The reference is pinned to exactly 10.0.11 with runtime assets excluded, the version read from the pinned image. The e2e login proves the bind at runtime, and the deps.json check proves the version match. |
| T-04-SC | Tampering | `Microsoft.Data.Sqlite.Core` package install | high | mitigate | NuGet, first-party Microsoft ownership, source `github.com/dotnet/efcore` — the same owner and repository that Phase 3 audited for `Microsoft.EntityFrameworkCore.Sqlite` and recorded as verdict OK (`03-01-PLAN.md`, T-03-SC). Version 10.0.11 is already resolved into the local NuGet cache transitively through that existing reference, so this adds no new origin. NuGet has no postinstall-script concept. Not `[ASSUMED]` and not `[SUS]`, so no human legitimacy checkpoint is required; the package-legitimacy gate's blocking checkpoint covers npm, PyPI, and crates only. |
