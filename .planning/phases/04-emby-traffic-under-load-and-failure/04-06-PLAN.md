<planner_notes>
**Discretion settled here** (`04-CONTEXT.md` § Claude's Discretion left these open):

- **Burst size: five.** Large enough that several callers are inside Jellyfin's shared `Guid.Empty` lock at once on a laptop and on a CI runner, small enough that five serialized Emby round trips stay well inside the file's runtime. The first-login path serializes by design, so a larger burst buys overlap that the test cannot observe and costs wall-clock time linearly.
- **New Emby user names: `bella`, `chris`, `dana`, `elton`.** None appears anywhere in `e2e/` or `tests/` today. `bella` and `chris` belong to `60-concurrent-logins.bats`, `dana` to `70-invalid-settings.bats`, and `elton` to `80-fingerprint-store.bats` in plan 04-07 — all four are added here in one edit to `setup_suite.bash`, because the rule is that every Emby user is created there and nowhere else.
- **File split: one topic per file**, `60-concurrent-logins.bats` and `70-invalid-settings.bats`, keeping `90-jellyfin-log.bats` last. Folding the invalid-settings cases into `10-login-checks.bats` would give the first file in the suite a settings mutation that every later file depends on being undone.
</planner_notes>

It takes a user name, a password, and a count; starts that many background subshells, each running `login_status "$JELLYFIN" "$user" "$password"` with its output redirected to its own file under `$BATS_TEST_TMPDIR` and with file descriptor 3 closed on the subshell; collects the process IDs; waits for every one of them before returning; then prints the collected files. Do not assert that any login was refused. When the burst does not overlap, the later logins resolve the account the winner created, take the save-password path, and return 200 — a correct outcome that a "require a refusal" assertion would fail on a loaded CI machine. <threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| unauthenticated client -> Jellyfin login endpoint | The burst drives the same endpoint an attacker would. |
| administrator -> plugin settings API | An invalid or credential-bearing URL is saved through the live API. |
| plugin -> Jellyfin log | A settings problem is written where an administrator reads it. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-24 | Information Disclosure | the configured Emby URL, with its credential, reaching the Jellyfin log | high | mitigate | `LogSettingsInvalid` takes only the static problem sentence. The third case configures a URL whose credential matches the pattern `90-jellyfin-log.bats` already scans the whole Debug-level log for, so the existing check fails if any code path ever writes the configured URL. |
| T-04-25 | Elevation of Privilege | a concurrent first-login race creating a second account or adopting one | high | mitigate | The burst asserts exactly one account with that name after five concurrent logins, and plan 04-04's unit test asserts the losing login makes exactly one `CreateUserAsync` call and no lookup by name. |
| T-04-26 | Denial of Service | a login returning HTTP 500 under concurrency | high | mitigate | The burst rejects `500` explicitly. Jellyfin catches only `AuthenticationException` from a login method, so any other escaping exception shows up here as a 500 and fails the test. |
| T-04-27 | Denial of Service | a bats run that never returns | medium | mitigate | Every backgrounded login closes file descriptor 3 and every process ID is waited for before the test function returns, which is the documented fix for the bats hang. The verify statement names a non-returning command as the failure. |
| T-04-28 | Tampering | this file leaving the plugin unusable for later files | medium | mitigate | `teardown_file` restores the Emby server URL and the API key in addition to `reset_plugin_config`, and the acceptance criteria require a later file to pass against the same running stack afterwards. |
</threat_model>
