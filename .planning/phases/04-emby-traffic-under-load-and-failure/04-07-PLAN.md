<planner_notes>
**Why the test moves the database to the host at all.** The fingerprint is a SHA-256 of a Jellyfin password hash, and Jellyfin generates a fresh random salt on every `CreatePasswordHash` call, so the hash — and therefore the fingerprint — is different on every login and cannot be computed by the test. The only source of a genuine record is the plugin itself. Building the JSON fixture out of the database the plugin just wrote is the one way to produce a "before the upgrade" file that is real rather than invented, and it is what makes the `Ready` assertion after the restart mean something.

**Why `sqlite3` on the host and not inside the container.** The Jellyfin image ships the SQLite native library for .NET but no command-line tool. `sqlite3` is present on macOS at `/usr/bin/sqlite3` (3.51.0, checked) and on GitHub's `ubuntu-24.04` runner image (3.45.1, listed in the runner-images manifest), so it needs no mise pin, the same way `docker` and `curl` need none. The helper checks for it and fails with a message naming it rather than skipping, because a silent skip turns this test into a green that proves nothing.
</planner_notes>

Add five helpers to `e2e/helpers.bash`, each with a comment naming what it does and, where it matters, why.

Export two path constants alongside the existing block: the database path inside the container, `/config/plugins/Jellyfin.Plugin.EmbyAuth/Jellyfin.Plugin.EmbyAuth.VerifiedPasswords.db`, and the legacy file path, `/config/plugins/configurations/Jellyfin.Plugin.EmbyAuth.VerifiedPasswords.json`. The first is Jellyfin's own `DataFolderPath` derivation — the plugins directory plus the plugin assembly's file name without its extension — and the second is `PluginConfigurationsPath`, which Jellyfin derives as the plugins directory plus `configurations`. Confirm both against the running container before relying on them; the first test asserts the database file exists there, which is how a wrong derivation surfaces immediately instead of as a confusing later failure.

`jellyfin_stop` runs `docker compose -f "$COMPOSE_FILE" stop jellyfin`. Stopping sends a termination signal and lets Jellyfin close its SQLite connections, which checkpoints and removes the write-ahead log, so the copied database is complete. Never copy the database out while Jellyfin runs.

`jellyfin_start` runs `docker compose -f "$COMPOSE_FILE" start jellyfin` and then `wait_until Jellyfin jellyfin_ready`.

`fingerprint_store_pull DEST` requires `sqlite3` on the host and fails with a message naming it when `command -v sqlite3` is empty. It copies the database out of the stopped container into `DEST` with `docker compose -f "$COMPOSE_FILE" cp`, and fails if the copy does not produce a file.

`fingerprint_store_push SOURCE` copies a database file from the host back into the container at the database path, then removes the write-ahead-log and shared-memory siblings inside the container so a stale log cannot be replayed over the file just pushed.

`fingerprint_store_remove` removes the database and both siblings inside the container, which is the state a server upgrading from the JSON store is in.

`legacy_fingerprint_file_write SOURCE` copies a JSON file from the host into the container at the legacy file path.

None of these may print a fingerprint, a hash, or a password to standard output. `docker compose cp` prints only paths; keep it that way and do not add a listing of the rows.

Add one line to `.claude/rules/e2e.md` under § Conventions: `sqlite3` must be on the host for `80-fingerprint-store.bats`, it is a system tool rather than a mise pin because macOS and the GitHub runner both ship it, and the helper fails rather than skips when it is absent.

Run `shellcheck -x e2e/*.bash e2e/*.bats` and `shfmt -d e2e`. Then run `scripts/dev-env.sh up` and `down`, because that script sources `helpers.bash` and the repo rule requires re-checking it after a change there.
