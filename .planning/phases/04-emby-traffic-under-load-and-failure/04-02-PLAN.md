<objective>
Make the Emby sign-out fire for every access token the plugin can read, including a login response that carries a token and no user name.

Purpose: AUTH-05. `EmbyClient.AuthenticateAsync` returns at `:88-92` when the response has no user name, so the sign-out at `:94` is unreachable for a response that carries an `AccessToken` and no name. Emby opened a session for that login and the plugin never ends it.
Output: The sign-out call moves ahead of the user-name check, the existing three-row theory splits because its rows stop agreeing, and the residual case D-02 documents becomes an explicit, named test instead of an accident.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Jellyfin -> Emby | A password crosses to Emby, and an access token crosses back. |
| Emby response body -> plugin state | Untrusted JSON of Emby's choosing is deserialized into typed records. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-07 | Information Disclosure | an Emby session left open by a response the plugin cannot parse | medium | accept | The token is inside the body that failed to parse, so no code can reach it. Plan 04-08 states the limit in `docs/how-it-works.md` rather than leaving the docs claiming the plugin ends every session. The login is still refused, so nothing is granted; only Emby's own session lives longer than needed. Accepted by D-02. |
| T-04-08 | Information Disclosure | the access token reaching a log entry | high | mitigate | `SignOutAsync` builds the token into the `Authorization` header only. Its two log partials take a user name and a status code. Task 2 asserts no captured entry contains the token, and `AssertNoSecretsLogged` covers the password and the API key on every test in the file. |
| T-04-09 | Spoofing | a response with no user name being accepted after the reorder | high | mitigate | The user-name check stays and still returns null; only the sign-out moves ahead of it. Task 1's new fact asserts `AuthenticateAsync` returns null for exactly that response, and the existing theory keeps its null assertions for the other shapes. |
| T-04-10 | Denial of Service | a slow or hanging sign-out delaying a login | low | accept | The sign-out runs on the same `HttpClient` with the existing 5-second timeout, and `SignOutAsync` already swallows an unreachable-Emby exception. The reorder adds this cost only to a response that is about to be refused anyway. |
</threat_model>
