<objective>
Import the records from an existing fingerprint JSON file into the SQLite store once, and never again.

Purpose: FPRT-04 and D-17. A server upgrading from the JSON store has records that took a real Emby login to earn. Losing them puts every affected user back to "Needs an Emby login". The marker for "already imported" has to survive a crash partway through, so the import and the marker commit together.
Output: A one-time import inside a single transaction, keyed on the database's own `user_version`, with the JSON file left untouched on disk.
</objective>

<planner_notes>
**Why `PRAGMA user_version` and not a marker row or the file's absence.** `user_version` is stored in the database header and its change is journaled with everything else in the transaction — measured directly with `sqlite3` 3.51.0: setting it to 7 inside a transaction and rolling back leaves it at 0. So the marker and the imported rows are one atomic fact. The file's absence is the marker D-17 warns against: a maintainer who restores the JSON file from a backup would trigger a second import. A marker row in a second table would work equally well but needs a second table for one bit.

**The end-to-end half of the import is plan 04-07**, which drives a real upgrade in the e2e stack. This plan is the unit half that ROADMAP criterion 2 also asks for.
</planner_notes>

  <action>
Widen the constructor to `public EmbyVerifiedPasswords(string databasePath, string legacyFilePath, ILogger<EmbyVerifiedPasswords> logger)` and keep the field for the second path. Every caller changes with it: the `AddSingleton` factory delegate in `PluginServiceRegistrator`, and `CreateStore` plus every direct construction in the test file.

In `PluginServiceRegistrator`, add `public const string LegacyVerifiedPasswordsFileName = "Jellyfin.Plugin.EmbyAuth.VerifiedPasswords.json";` — the same name the store used before this phase — and pass `Path.Combine(paths.PluginConfigurationsPath, LegacyVerifiedPasswordsFileName)` as the second constructor argument. `PluginConfigurationsPath` is where the old store wrote, so this is the file a real upgrade actually has. Give the constant an XML doc saying it is an import source that the plugin reads at most once and never writes.

In `EnsureInitialized`, after the `CREATE TABLE IF NOT EXISTS` statement and before setting `_initialized`, call a new `private void ImportLegacyRecords(SqliteConnection connection)`. Keep the table creation and the WAL pragma outside the import's transaction, so a failed import still leaves a working, empty table.

`ImportLegacyRecords` opens an immediate transaction with `connection.BeginTransaction(deferred: false)` — the overload exists on `SqliteConnection` in 10.0.11 — so two processes racing the same import cannot both get past the check. Inside it: read `PRAGMA user_version` as a scalar and return without committing when it is not zero; that is the already-imported case and the common one. Otherwise, when `File.Exists(legacyFilePath)`, deserialize the file into `Dictionary<Guid, string>` and execute `INSERT INTO VerifiedPasswords (UserId, Fingerprint) VALUES ($userId, $fingerprint) ON CONFLICT(UserId) DO NOTHING;` once per entry, binding both values as parameters and writing the key as `Guid.ToString()`, which is the same lower-case dashed form the JSON file used and the same form `Record` writes. Do nothing on conflict rather than replacing: a row already in the table was written by a login and is newer than anything the file holds. Then execute `PRAGMA user_version = 1;` and commit.

Catch `JsonException`, `IOException`, and `UnauthorizedAccessException` around the file read and the inserts, log once through a new `LogImportFailed` partial at `LogLevel.Error` that names the legacy file path and says the plugin will try again the next time Jellyfin starts, and return without committing. Disposing the uncommitted transaction rolls back both the rows and the `user_version` change together, which is what makes a crash partway safe: nothing is half-imported and the marker stays unset. `user_version` is journaled with the rest of the transaction — verified directly against `sqlite3` 3.51.0 by setting it inside a transaction and rolling back, which left it at zero.

Never write, move, or delete the legacy file. A server that rolls the plugin back still has its records, and a crash after such a write would lose rows the transaction had not committed.

Add nothing to the log but the path: no user ID, no fingerprint, no count that could be read as a user list.

Write all six tests in the `<behavior>` block before the import exists; each is red because the constructor does not yet take a second path. `prek` runs `mise run test` on commit and blocks a commit with a failing test, so follow the established convention (STATE.md): the red commit carries them as `[Fact(Skip = "...")]` naming this task, and the green commit unskips them. <threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| on-disk JSON file -> plugin state | A file an administrator or an earlier version wrote is deserialized into typed records. |
| plugin configuration folder -> plugin data folder | Data crosses from one Jellyfin-owned directory into another. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-19 | Tampering | the import path reading or writing outside the plugin folders | high | mitigate | Both paths come from `IApplicationPaths` and a compile-time constant file name; neither is built from user input, a setting, or an environment variable, so no traversal input exists. The import reads one fixed path and writes only through parameterized SQL into the database it opened. A source assertion requires `ImportLegacyRecords` to contain no file-writing call at all. |
| T-04-20 | Tampering | a hand-edited JSON file injecting a fingerprint for another user | high | mitigate | The file is readable and writable only by whoever can already write Jellyfin's plugin configuration folder, which is the same identity that can edit Jellyfin's own user database. A fingerprint is a SHA-256 of a password hash and cannot be inverted into a password, and it opens no account on its own: `EmbyAuthenticationProvider` still refuses every Emby-method login that Emby does not accept. `ON CONFLICT DO NOTHING` also stops a crafted file from overwriting a genuine record. |
| T-04-21 | Denial of Service | a very large JSON file read into memory at startup | low | accept | The file holds one fingerprint per Jellyfin user on a single-server install, and the previous store read the whole file into memory on every login. This reads it at most once per process. |
| T-04-22 | Information Disclosure | user IDs or fingerprints reaching the log through an import failure | high | mitigate | `LogImportFailed` takes the file path and the exception only. `JsonException` messages name a byte position and a type, never a value from the document. `NoLogEntryNamesAHashOrAFingerprint` from plan 04-01 covers the store's other paths. |
| T-04-23 | Repudiation | a second import silently resurrecting deleted records | medium | mitigate | The marker and the rows commit together, and `Import_DoesNotRunASecondTime` asserts a deliberately deleted row stays deleted across a restart with the file still present. Plan 04-07 asserts the same through the real server. |
</threat_model>
