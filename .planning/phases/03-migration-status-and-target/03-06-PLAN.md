<objective>
Close MIGR-01's server side. The settings page offers only login methods Jellyfin reports as enabled, but a dropdown in a browser is not a control — a caller posting straight to Jellyfin's plugin configuration API never sees it. This plan puts the refusal where every save has to pass, and wires the password-set path to the setting that governs it.

Two things land here. The refusal: `EmbyAuthPlugin` overrides `UpdateConfiguration`, checks both targets against Jellyfin's live enabled-provider list, and throws without writing anything when one does not hold up. The password-set path: `EmbyAuthenticationProvider.ChangePassword` stops hardcoding Jellyfin's Default and sends the user to the password-set target instead, which by default is the migration target.

Purpose: MIGR-01 says the plugin refuses a value that is not one of the enabled login methods. Without this plan the plugin only *hides* such values, which is a different and much weaker claim.

Output: a pure validator with exhaustive unit tests, an override that calls it, and a password-set path that reads a setting.
</objective>

  <action>
Create `src/Jellyfin.Plugin.EmbyAuth/MigrationTargetValidation.cs` holding `internal static class MigrationTargetValidation` with one method:

`internal static string? FindProblem(PluginConfiguration? configuration, IReadOnlyList<NameIdPair> enabledLoginMethods)`

It returns a plain-language message or null, following `EmbyAuthSettings.FindProblem`'s early-return chain. A null configuration is a problem. A null, empty, or whitespace `MigrationTarget` is a problem. A `MigrationTarget` equal to `PluginConfiguration.RemainOnEmbyLoginMethod` is accepted and short-circuits the rest of that check, because it names no login method at all. A `MigrationTarget` equal to `EmbyAuthenticationProvider.ProviderId` is a problem: this plugin's own method appears in Jellyfin's enabled list because `IsEnabled` returns true, but it is not a destination — Remain on Emby Login is how an administrator asks for no move, and accepting both spellings would give one meaning two encodings that the move code and the settings page would then have to keep agreeing about. A `MigrationTarget` matching no `Id` in `enabledLoginMethods` is a problem. Then the same three rules apply to `PasswordSetTarget`, except that a null or empty value is accepted because it means the migration target governs that move.

The validator takes the already-resolved list rather than `IUserManager` so it stays a pure function with no Jellyfin dependency to stand up, which is what makes the nine rule behaviors cheap to test exhaustively. It lives in its own file rather than on `EmbyAuthSettings` because `EmbyAuthSettings` is deliberately the shape-only validator plan 04 kept free of any live Jellyfin state, and folding a list-dependent check into it would erase that line.

Each message names the setting in plain language — the migration target, or the target used when a password is set in Jellyfin — and says the value is not a login method Jellyfin reports as enabled. It must not contain the value: an administrator can post anything to the settings API, and a message that echoes it puts whatever was posted into a Jellyfin log that is read by more people than posted it. That is the same rule `.claude/rules/plugin.md` §Settings applies to the Emby server URL, which can carry credentials.

In `EmbyAuthPlugin`, add `IServiceProvider serviceProvider` as a third constructor parameter with an XML `<param>` doc. Jellyfin builds plugin instances with `ActivatorUtilities.CreateInstance` over the application's service provider — verified during planning against `PluginManager.CreatePluginInstance` — so an added parameter the container can resolve is supplied, and `IServiceProvider` always resolves.

Override `UpdateConfiguration`. Its base declaration on `BasePlugin<TConfigurationType>` is `public virtual void UpdateConfiguration(BasePluginConfiguration configuration)`, verified during planning by reflection against the installed `MediaBrowser.Common` 12.1.0 assembly. The override resolves `IUserManager` from the stored service provider *inside the method body*, never in the constructor: `IUserManager` depends on every login method including this plugin's own, so holding it from construction time would be the cycle `.claude/rules/plugin.md` warns about. Resolving it when an administrator saves settings is long after the provider graph exists.

The override casts the incoming configuration to `PluginConfiguration`, calls `MigrationTargetValidation.FindProblem` with `userManager.GetAuthenticationProviders()`, and when a problem comes back logs one Error entry with that message and throws `ArgumentException` carrying it, without calling the base method — so nothing is written and the previous settings stand. When no problem comes back it calls the base method and lets Jellyfin save as it does today. Resolve `ILogger<EmbyAuthPlugin>` from the same service provider inside the method.

Throwing is what makes this a refusal rather than a warning: Jellyfin's plugin configuration endpoint does not catch it, the request fails, and the settings page's existing save-failure handler shows its message and points at the Jellyfin log, where the specific reason is waiting. Do not swallow the problem and save anyway, and do not silently correct the value to something else.

Write `MigrationTargetValidationTests.cs` covering the nine rule behaviors. Write `EmbyAuthPluginTests.cs` with one reflection test asserting `EmbyAuthPlugin` declares its own `UpdateConfiguration` method — constructing the plugin needs `IApplicationPaths` and `IXmlSerializer` fakes and would write an XML file, and the end-to-end proof that the override actually refuses a save belongs to plan 07's real server, not to a unit test standing up half of Jellyfin.

On the move outcome, assign the resolved provider id to the user's login method and keep the existing Information-level log, reworded so it no longer says Default — it states that the administrator or the user set a password in Jellyfin for the named user, who now moves to the configured login method.

On the remain outcome, save the hash and leave the login method alone. This is D-12 applied to this path: Remain on Emby Login means no path moves anyone, and there is no hidden fallback. The method stays synchronous and takes no new dependency: `configurationSource` is already a constructor parameter.

Leave the password-reset branch exactly as it is — an empty new password clears the saved password and the user stays on the Emby login method, because a Default account without a password opens with a blank password. That reasoning is unchanged by this plan and its test must still pass untouched.
