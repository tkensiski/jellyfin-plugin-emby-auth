<objective>
Prove on a real server what the unit and jsdom suites can only prove in isolation: that a migration ending on a login method other than Jellyfin's Default actually works, and that the plugin really refuses a target Jellyfin does not report as enabled.

ROADMAP criterion 7 needs a second login method to migrate to, and the end-to-end stack has none. D-21 fixes it as JellyfinSecurity v2.6.1's Jellyfin-12 build, pinned and checksum-verified, installed beside this plugin in the shared container — which is the production topology for a migration that ends there, not a compromise. D-23 draws the scope line: the test ends at the hand-over, and everything past it belongs to JellyfinSecurity.

RESEARCH.md leaves one question genuinely unresolved from documentation: whether JellyfinSecurity is inert on a completely unconfigured install. This plan answers it with a live check before anything is built on top of it.

Purpose: this is the only evidence in the phase that comes from a real Jellyfin and a real Emby. Everything else is a double.

Output: a pinned, checksum-verified install of a second real login method, an end-to-end test file covering the hand-over and the refusals, and documentation that matches what the plugin now does.
</objective>

The hand-over test, which is ROADMAP criterion 7:

Set the migration behavior to keep Emby in charge and the migration target to JellyfinSecurity's id, in one `set_plugin_config` call. Keeping Emby in charge makes the move a deliberate, observable step rather than a side effect of the login, and it exercises the migration task's target parameter, which is the path plan 04 changed. Then record the count of Emby login requests for her name, log in again with the same password, assert 200, and assert the Emby count did not change. That last assertion is the whole point: the password Emby verified now opens the account without Emby, which is the hand-over.
