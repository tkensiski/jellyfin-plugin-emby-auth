Rewrite the Migration section of the settings page against the response plans 01 and 03 built.

UI-03: the list follows the migration task until it actually finishes, instead of reloading once after a fixed three seconds and showing whatever the server happened to have at that instant. Purpose: everything before this plan is invisible to the administrator. This is where the phase becomes something a person can see and act on.

Output: a polling loop with two distinct stop conditions, two dropdowns, three conditional messages, and jsdom coverage of each against the shipping page file.

Delete the fixed three-second reload at line 137 outright, per D-06. Phase 02 D-11 deliberately left it untested precisely so this change churns no existing test.

Replace it with a `setInterval` loop at a 2000 ms cadence, per D-04. No websocket: the `ScheduledTasksInfo` socket API has never been used in this repository and the jsdom harness would need a socket stub, while polling reuses the one endpoint and the `ApiClient.getJSON` stub that already exists.

**Stop condition, and one deliberate refinement of D-03.** D-03 asks the page to record when the POST returned and stop only when the task is Idle *and* the last run ended after that moment. Implement the same intent by comparing values rather than clocks: before issuing the Run request, remember the `LastEndTimeUtc` the page last saw; stop when the task reports Idle *and* reports a last end time that is present and different from the remembered one. This closes exactly the window D-03 is about — `QueueIfNotRunning` returns 204 while the task is still Idle, so a page that stopped at the first Idle would render the old list — without ever comparing a browser clock to a server timestamp, which would misfire whenever the two disagree. `e2e/helpers.bash` already solves the same problem the same way. Note the refinement and the reason in a comment on the stop condition.

**The start-window cap.** Count polls since the run request. If ten of them pass — about twenty seconds at the 2000 ms cadence, which is D-05's "about 20 seconds" — with the task never reported as anything but Idle and the last end time never changing, stop polling and show a message saying the migration did not start and the Jellyfin log has the detail. Counting intervals rather than reading a clock keeps the whole loop on one timer, which is also the only timer the tests need to mock. The cap applies only to the start window: once a poll observes the task as Running or Cancelling, the counter stops mattering and the loop follows the task for as long as it runs, per D-05, because the server is stating it is still working and a migration of many accounts can outlast any fixed window.

**One request at a time.** Hold a flag while a migration-status request is in flight and skip the tick rather than stacking a second request behind a slow one.

**Starting without a Run click.** When a load observes the task Running — an administrator started it from Dashboard > Advanced > Scheduled Tasks — start the same loop with no start-window cap, since the run has already begun, and stop when it reports Idle.

**Stopping.** Clear the interval when the loop stops, when the run request fails, and on the page element's `pagehide` event, so a settings page the administrator navigated away from stops calling the API.

**The absent task.** The response's task field is null when Jellyfin has no worker registered for the migration task. Render that as its own condition — the section says the migration task is not registered and names the Jellyfin log — never as an idle task that has never run, which would look identical to a healthy server that simply has not run the migration yet.

In `tests/js/testHelpers.js`, add what the polling tests need: a way for `stubApiClient.getJSON` to resolve with a different response on each successive call, so a test can script Idle then Running then Idle-with-a-new-end-time; and a small helper that pairs `context.mock.timers.tick` with the existing `flush`, since the mocked timer fires synchronously while the page's own promise chain still needs real microtask turns to settle. Enable only the `setInterval` API in the mock, so nothing else in jsdom is affected.

Add the nine behaviors as jsdom tests. Assert on observable page state and on `api.migrationStatusCalls`, never on the interval handle.
